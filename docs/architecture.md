# Устройство проекта

Приложение остаётся модульным монолитом NestJS и отдельным Next.js frontend. Kafka переносит события между доменными областями, а не превращает каждый класс в микросервис. SQLite, HTTP API, outbox worker и consumer работают в одном экземпляре backend. Это осознанная граница текущего запуска, в том числе в Kubernetes.

## Backend

| Область | Ответственность | Где искать |
| --- | --- | --- |
| Identity | Регистрация аккаунта, публичные события профиля, атомарная запись аккаунта и outbox | `backend/src/identity` |
| Social | Подписки и лайки, инварианты связей и переходы состояния | `backend/src/social` |
| Discovery | Проверка событий, inbox и проекция каталога авторов | `backend/src/discovery` |
| Catalog | Ограниченные запросы ленты, сортировка и метаданные страниц | `backend/src/catalog` |
| Transport | HTTP-контроллеры, Kafka producer/consumer, bounded health checks | существующие модули, `events`, `health` |
| Persistence | Единый Prisma client и SQL-миграции | `prisma`, `backend/prisma/migrations` |

В выделенных областях `domain` содержит правила и контракты без framework/ORM. `application` координирует сценарий через порты. `infrastructure` реализует доступ к Prisma и внешним ресурсам; Nest-модули связывают зависимости. В CI `scripts/check-boundaries.mjs` проверяет импорты домена и application, включая re-export, require и dynamic import. Это проверка направления зависимостей, а не доказательство всей корректности архитектуры.

Остальные модули медиа, администрирования и комментариев пока сохраняют legacy-структуру. Их нельзя считать полностью переведёнными на DDD. При последующих изменениях переносите конкретный сценарий вместе с его инвариантами и тестами, а не создавайте пустые слои для каждого метода.

## Данные и события

HTTP-регистрация завершается после транзакции SQLite, содержащей аккаунт и outbox-событие. Доступность брокера не определяет успех этой транзакции. Worker отправляет сохранённые события и отмечает подтверждённые; авария между отправкой и отметкой может привести к повторной доставке.

Consumer проверяет контракт события и атомарно обновляет inbox и каталог авторов. Поэтому повтор сообщения не должен повторно применять бизнес-изменение. Каталог авторов доступен через `/creators`; его обновление **eventually consistent**: сразу после регистрации автор может ещё не появиться. При отказе брокера/consumer запись аккаунта сохраняется, а проекция догоняет после восстановления. Старые события должны оставаться читаемыми при обновлении приложения; тесты включают прежний контракт.

Тема `flowing.user.registered.v1` сохраняется для совместимости с существующими данными Kafka. Публичные события профиля не должны включать email, пароль или JWT. Изменения event schema требуют совместимого parser и миграционного сценария, а не только смены TypeScript interface.

Связи подписок/лайков уникальны по паре участников, счётчики изменяются вместе со связью. Миграции исправляют существующую схему без reset пользовательской БД; исторические конфликтующие записи архивируются по описанным в SQL правилам. Не удаляйте старые миграции и не заменяйте `migrate deploy` на `db push` в рабочем запуске.

## Frontend

`frontend/features` хранит связную логику пользовательских функций, `components/ui` — общие примитивы, `app` — маршруты. Лента получает ограниченные страницы вместо полного графа видео/комментариев/просмотров. Пагинация offset-based: при добавлении или изменении рейтинга роликов между запросами набор может сдвигаться; это не snapshot поисковой выдачи.

Сортировка и загрузка следующих страниц должны сбрасывать предыдущий pagination state согласованно. Карточка не должна создавать собственные одинаковые запросы пользователя/подписок. Обработчики проигрывания и прогресса изолированы: каждый `timeupdate` не перерисовывает всю ленту. При смене активного видео, уходе со страницы и скрытии вкладки воспроизведение прекращается, обработчики очищаются. Формы авторизации недоступны до hydration и имеют безопасный POST fallback.

## Инфраструктура и проверки

Compose остаётся основным простым запуском. Клиентское демо с туннелем изолировано от тестового Compose. Kubernetes — отдельный проверяемый вариант развёртывания: [запуск и ограничения](../k8s/README.md). Он не даёт автоматической HA для SQLite или одного Kafka broker; для этого нужны отдельная миграция СУБД, координация workers и несколько брокеров.

Pipeline проверяет dependency boundaries, типы/сборки, доменные и API-тесты, браузер, Kafka и восстановление зависимостей. После них запускается отдельный kind smoke, включая замену pod и сохранение данных на PVC. [Критерии независимого review](review-checklist.md) фиксируют, по каким требованиям принимается этот набор изменений.
